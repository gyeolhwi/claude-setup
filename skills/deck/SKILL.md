# /deck — 기획안 → 발표자료

두 단계로 나뉜다. **1단계 결과(기획안)를 사용자가 승인하기 전에는 절대 2단계로 넘어가지 않는다.**

| 경로 | 용도 |
|---|---|
| `scripts/deck.js` | 검사(check)·생성(build)·미리보기(render) |
| `references/plan-format.md` | 기획안 고정 형식 + 형태(layout) 17종 카탈로그 |
| `references/tone.md` | 원본 문구 → 슬라이드 문구 재구성 규칙 |
| `examples/popup-automation.plan.md` | 완성 예시 (`presentation.md` → 기획안) |

`D=~/.claude/skills/deck/scripts/deck.js` 로 표기한다.

---

## 1단계 — 기획안 만들기 (`/deck plan`, 또는 주제·자료를 받았을 때)

**입력 받기** — 기획안을 쓰기 전에 아래 항목을 확보한다.

| 항목 | 필수 | 예 |
|---|---|---|
| 주제 | ✔ | 팝업 이미지 제작 자동화 |
| 목적 | ✔ | 경영진 승인 / 팀 공유 / 고객 제안 |
| 대상 | ✔ | 디자인팀·경영진 (비개발자 포함) |
| 참고 자료 | 권장 | 파일 경로(md·txt·pdf 등) 또는 붙여넣은 메모 |
| 분량 | | 10장 / 15분 |
| 강조점·톤 | | 숫자 효과 강조, 발표자 관점(개발자 시점 등) |
| 색상 | | 프리셋 이름(blue·navy·green…) 또는 #HEX — 없으면 blue |

- `/deck` 만 호출되어 아무 정보가 없으면, 작업 폴더의 문서 파일(`*.md` 등)을 찾아본 뒤 아래 질문을 **그대로** 보내고 멈춘다(자유 입력이라 AskUserQuestion 대신 텍스트):

  ```
  기획안을 만들 정보를 알려주세요. (필수: 1~3)
  1. 주제:
  2. 목적: (예: 승인 받기 / 팀 공유 / 고객 제안)
  3. 대상:
  4. 참고 자료: (파일 경로 또는 내용 붙여넣기) — 이 폴더에서 찾은 문서: <목록 또는 "없음">
  5. 분량·강조점: (선택)
  6. 색상: (선택 — blue, navy, indigo, purple, teal, green, orange, red, black 또는 #HEX)
  ```
- 일부만 받았으면 빠진 필수 항목만 같은 형식으로 묻는다. 참고 자료가 주어지면 주제·목적이 자료에서 분명할 때 그 값을 쓰고, 대상만 묻는다.
- 참고 자료가 없으면 사용자가 준 문장만으로 구성한다(사실·수치를 지어내지 않음 — 장 수가 적어져도 됨).

1. `references/plan-format.md`, `references/tone.md`, `examples/popup-automation.plan.md` 를 읽는다.
2. 스토리 순서를 정한다(기본 골격, 내용에 없는 칸은 생략):
   표지 → 배경·문제 → 해결 방향(전후 비교) → 방법·흐름 → 구조·세부 → 현황 → 향후 계획 → 효과·마무리
   - 한 슬라이드 = 한 메시지. 분량 희망이 없으면 8~14장.
   - 섹션은 3~7개.
3. 슬라이드마다 내용에 맞는 형태를 고른다:

   | 내용 | 형태 |
   |---|---|
   | 문제·현황 + 대표 수치 | `stat-list` |
   | 전후/옵션 비교 | `table` |
   | 순서 있는 절차 | `flow` (짧은 라벨) · `pipeline` (설명형 단계) |
   | 단계·항목별 세부 기능 | `step-cards` |
   | 기술·사양 목록 | `spec-list` |
   | 폴더·구성 구조 | `tree` |
   | 현재 vs 전환 구조 | `lanes` |
   | 대상별 상세 내역 | `detail-cards` |
   | 진행 상태 한눈에 | `status-grid` |
   | 이유·원칙 3가지 | `points` |
   | 사용 시나리오 | `chat` |
   | 실행 단계 계획 | `stages` |
   | 장기 로드맵 | `roadmap` |
   | 실제 결과물 이미지 | `images` |
   | 결론 수치 | `closing` (마지막 장) |

   같은 형태를 연속 3장 이상 쓰지 않는다. 첫 장은 `cover`, 마지막 장은 `closing` 이 기본.
4. `tone.md` 규칙대로 문구를 재구성한다. **원본에 없는 사실·수치는 만들지 않는다.**
5. 작업 폴더에 `<주제-영문-kebab>.plan.md` 로 저장 (`plan-format.md` 형식 그대로, 2번 표는 비워 둠).
6. `node $D check <plan.md>` — 형식·분량 검사 + 구성표/헤딩 자동 생성. **오류가 0건이 될 때까지 문구를 줄이거나 형태를 바꿔 다시 실행.**
7. 사용자에게 보고(아래 형식 고정) 후 검토를 요청하고 멈춘다:

   ```
   기획안: <절대 경로>
   <「2. 구성 한눈에 보기」 표를 그대로 붙여넣기>
   검토 후 수정할 슬라이드 번호와 내용을 알려주세요. 승인하시면 PPT를 생성합니다.
   ```

**색상 변경 요청**("초록색으로", "#2B5BD7 로")은 개요 표 `색상` 값만 바꾼다. 이미 PPT 를 만든 뒤라면 바로 build·render 까지 다시 한다.

**수정 요청**을 받으면 해당 yaml 블록만 고치고 다시 `check` → 바뀐 행만 보고.

## 2단계 — PPT 생성 (`/deck build`, 또는 "승인", "이대로 만들어줘")

1. `node $D build <plan.md> -o <같은 폴더>/<이름>.pptx` — 검사 통과 시에만 생성된다.
2. `node $D render <pptx>` → `<이름>_preview/grid.jpg` 와 `slide-NN.jpg` 생성.
3. grid.jpg 를 보고, 의심 가는 장은 slide-NN.jpg 로 확대 확인:
   글자 잘림·겹침, 빈 카드, 이미지 누락 자리표시, 줄바꿈이 어색한 단어.
   문제가 있으면 **기획안 문구를 고쳐** 다시 build·render (pptx 직접 수정 금지 — 기획안과 결과가 항상 일치해야 함).
4. 보고: pptx 경로, 장 수, 검수에서 고친 점(있다면).

## 고정 규칙 (일관성)

- 디자인(색·글꼴·위치·크기)은 `deck.js` 에만 있다. 슬라이드마다 임의 스타일을 추가하지 않는다. 새 형태가 정말 필요하면 사용자 승인 후 `deck.js` 의 `LAYOUTS` 에 추가하고 `plan-format.md` 카탈로그도 함께 갱신.
- 글꼴은 Pretendard. 발표 PC에 Pretendard 가 없으면 대체 글꼴로 보이므로 필요 시 사용자에게 안내.
- 화면 비율 16:9 (20 × 11.25 in), 흰 배경 + 강조색 하나, 마무리 장만 강조색 배경. 강조색은 기획안 개요의 `색상` 줄로만 바꾼다(`plan-format.md` 「색상」). 색 변경은 기획안 한 줄 수정 후 build 만 다시 하면 된다.
- 발표자 노트는 모든 장 필수.

## 문제 해결

- `{ } 안의 값에 쉼표가 있으면 "따옴표"로 감싸세요` → 해당 값을 `"..."` 로.
- `분량 초과` → 문구를 줄이거나 항목을 나눈다. 글자 크기를 줄여서 해결하지 않는다.
- render 결과에 한글이 안 보이면: `brew install --cask libreoffice` 재설치 여부와 `scripts/fontconfig/fonts.conf` 경로 확인.
- 의존성 누락 시: `cd ~/.claude/skills/deck/scripts && npm install`.
